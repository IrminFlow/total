# Total — project guide

Total is a **fully offline accounting app for macOS** (Electron + React + TypeScript + SQLite): Tally-grade double-entry books with GST returns, invoicing/PDF, inventory + manufacturing (BOM), banking reconciliation, payroll, multi-currency, Tally XML import, and optional live e-invoice/e-way-bill filing via the NIC APIs. All user data lives in `~/Documents/total/` — no cloud, no accounts. The repo also contains the marketing site (`site/`, Next.js, deployed on Vercel).

GitHub: **public repo `IrminFlow/total`** (made public 2026-10-07) (HTTPS remote, `gh` credential helper).

## Hard rules & conventions

- **Money is integer paise everywhere**; quantities are integer thousandths (`qtyMilli`). Floats never touch amounts. Formatting/parsing only via `src/shared/money.ts`.
- **Voucher lines are the source of truth** — every report is computed from `voucher_lines` + opening balances at query time. Never denormalise balances.
- The engine (`src/shared/`) stays pure: no Electron, no DB. Anything testable goes here or in pure main-side modules; **vitest must never import better-sqlite3** (it's built for Electron's ABI, not system Node).
- Every IPC payload is Zod-parsed in `src/main/ipc.ts`; handlers return `{ ok, data | error }`.
- Debit/credit: signed balances are dr-positive; Tally XML import converts Tally's negative-=-debit convention.
- UI: theme tokens are `--t-*` CSS vars on `[data-theme]`, mapped through Tailwind `@theme inline` — components use token utilities only. The amber `.kbar-row` selection bar on `<tr>` uses an inset box-shadow, **never `::before`** (a `tr::before` renders as a phantom first cell).
- Vouchers are soft-deleted (`vouchers.deleted_at`, moved to the bin) — every new SQL query touching `vouchers`/`voucher_lines` must filter `deleted_at IS NULL` (see `NOT_DELETED` in `src/main/services/vouchers.ts`) unless it's explicitly reading the bin, `getVoucher`, or `nextVoucherNumber`.
- Income/expense ledgers reset every financial year (`src/shared/yearOpening.ts`); profit for a period is defined once (`pnlLedgerAmounts` in reports.ts) and excludes year-end closing journals (`vouchers.is_year_end_close`, migration 018). Closing journals are immutable — bin to reopen a year. Any new report that touches P&L figures must go through these helpers, never re-derive them.
- Audit trail (MCA rule 3(1) edit log, WP 3.8): every write goes through `writeAudit` (services/audit.ts) with the whole before/after. `audit_log` is append-only and hash-chained (migration 031 triggers + `src/shared/auditChain.ts`) — never UPDATE/DELETE it; only `pruneAudit` may delete, and never while `auditTrailRequired` (default on). A new write IPC channel must be mapped in `src/main/auditCoverage.ts` and a new entity added to `src/shared/auditEntities.ts` — `auditCoverage.dbtest.ts` fails otherwise. A migration that inserts audit rows with raw SQL gets them sealed by the runner; one that rebuilds `audit_log` must recreate both triggers.
- Secrets live in `src/main/services/secrets.ts` (safeStorage, `<dataRoot>/secrets.json`), never in a company DB or backup: NIC credentials under `companyScope(slug)`, the AI provider key under scope `'app'` (shared by all companies; only a hint like `…a1b2` ever reaches the renderer).
- AI agent (WP 5.1 / Phase 5, migration 036): every AI call is made from main (the renderer never talks to the network); all AI code lives in `src/main/ai/` (shapes the renderer needs in `src/shared/ai.ts`); only `ai/provider.ts` imports `openai` and only main touches the network (`networkBoundary.test.ts`). Tools are `defineTool` entries over existing services — `read` or `draft`, never writing the books; `draft_voucher` writes `ai_drafts` only — the user opens it in VoucherEntry (`aiDraftId`) and saves through `voucher:save`, which consumes it, so roles, lock dates, credit holds and closing-journal immutability all apply. Tool results format money (the model quotes). Settings are per company (meta `ai`, off by default, data notice first); what is sent is masked/pseudonymised per the privacy toggles (GSTIN/PAN/IFSC/account numbers, optional party aliases — party names only, never other ledgers) and logged in `ai_outbound_log` (sizes and a hash, never the payload), costs in `ai_usage`; the data notice is re-accepted when its version changes. The key lives in the secret store (scope `app`). `TOTAL_AI_MOCK=1` (scratch dir, unpackaged only) replays the MockProvider for tests/e2e. The app-wide key may be changed only by the owner of a company that has users; in a company without users it is refused while any other company has users, else needs an explicit confirmation — every change also goes to the app-level, append-only `<dataRoot>/ai-key-audit.jsonl`. The model never computes money: `numbers.ts` checks every figure in an answer against the tool-result text the model actually saw (post-trim) across the thread and the panel flags the rest; a draft the question did not ask for is flagged `unrequested`. Never add placeholder migrations (`migrations.dbtest` fails on a comment-only entry).
- AI chat panel (WP 5.2): the assistant is a `DockedDrawer` beside every screen (⌘J; `components/ai/AssistantPanel.tsx`, also the host that turns "Explain this" and the palette's Ask AI row into a question). The screen context (`src/shared/aiExplain.ts` — screen, title, period, params, the figure to explain) is built by the renderer (`lib/aiContext.ts`; screens add selections with `useAiScreenContext`) and its `screenContextLines` are both the panel's "what the model is told" strip and the system-prompt lines; it is logged in `ai_outbound_log.context_json`. "Explain this" (`kit/ExplainButton`, via `lib/explain.ts` so the kit never imports the AI client) shows only while AI is ready: DataTable money cells (column `explainable`, default on for money), money StatTiles (`explain` prop adds ids), StatementTree lines. Explanations come from the `explain_figure` tool (breakdown, previous period, anomalies — computed by the tool, never the model); `current_screen_data` returns what the current screen shows. Sourced figures carry `AiFigure.source` (the row they were found in) and render as chips. Navigation requests ("open the ledger for X") are resolved by the search service, never the model.
- Assistants (WP 5.5, migration "assistants" — 044; `services/assistants.ts`, `ipcAssistants.ts`, Analysis → Assistants): deterministic engines, AI optional. Month-end close checklist (`shared/closeChecklist.ts`) is computed from existing services at query time (brs + unmatched statement lines, `partyAllocation` unapplied credit, overdue bills, GST "prepared" = exported JSON snapshot, tagged TDS/TCS payable balances + `tdsEligible`, `negativeStock`, GRNI/GDNI pending notes, Suspense A/c, PDCs, depreciation runs, missing regular P&L ledgers, exceptions, open drafts / optional vouchers, lock date); only user marks are stored (`assistant_marks`, done / n/a / dismissed / resolved, audited `assistant_mark`) with the FINGERPRINT of the figures they were made on — a changed finding re-opens the row. TDS / TCS payable is FIFO: deductions by month vs every payment up to today, each part dated by its own month's due date. Anomalies (`shared/anomalies.ts`): stable keys (with the amount, so an edited voucher re-surfaces), bill-number duplicates within one FY (rule 46(b)) using recon2b's `normalizeInvoiceNumber`, back-dated vs the lock's SET date (audit) with imports skipped, GST rate check without cess on the goods side only incl. rated ledger lines, outliers with a floored spread (max(sd, 10% of mean, ₹100)), BigInt z-scores in thousandths, GST rates in basis points, 12-month baseline, weekly offs / holidays / thresholds in meta `assistants`. GSTR-2B: the imported JSON is kept per return period (`gst2b_statements`, audited without its content; the GSTR-2B screen stores a copy best-effort); `shared/gst/mismatch2b.ts` categorises the WP 3.4 reconciliation (missing in books / in 2B, amount / period / GSTIN differs) with draft PLANS built through the WP 5.3 pipeline (`buildLedgerInvoiceDraft`: accounting form, rehearsed save, sources + assumptions; screen drafts have source 'assistant'), never posted. Mismatch keys are identifier-free (letters-only hash) so masking can't break them; debit notes are dated the working date and netted into their purchase (same party + reference) before matching; rev = Y gets no draft (purchase form / RCM self-invoice), itcavl = N books the tax as cost, s.16(4)-barred invoices get a note, b2ba / cdnra are labelled; a duplicate (same supplier + bill this or last FY, or an open draft) is refused. Report from a question: `shared/reportBuilder/nl.ts` — the model (or the deterministic phrase mapper, no AI) produces a request with NAMES, resolved and validated by the WP 6.1 schema, run by `runReport`; the link opens the builder pre-filled (`report-builder` screen `model`). AI tools `close_checklist` / `gst_2b_mismatches` / `find_anomalies` / `build_report` (read) and `draft_gst_2b_fix` (draft) call the same services; "Run with AI" pre-runs a read tool (`aiSendSchema.preCall`, `AI_PRE_CALL_TOOLS`) so the turn starts from its result. Due-date / ITC rules cited in `shared/assistantSources.ts` with the UNVERIFIED list (GSTR-1 11th, QRMP, 2B schema).
- i18n (WP 8.2, `src/shared/i18n/`): `t(key, vars, lang)` with ICU-lite `{name}` / plural / select (`format.ts`); `catalogues/en.ts` is complete and the source of every key (flat, dotted, grouped by screen), `hi` / `hinglish` fall back to `en` per key — except the simple-mode namespaces, complete since WP 10.4 (below) (a key outside `en` fails typecheck + the parity test; an empty translation falls back to `en` too; an unknown key renders its last segment in production, never blank, and the key + one warning in dev). The user's language is a renderer setting (`lib/i18n.ts` `useLanguage` / `useT`, localStorage, per company + user when signed in; Settings → How Total looks → Language); main-side strings use `companyT(db)` (`src/main/i18n.ts`, meta `ui.language`, missing = en). **Simple-mode strings always go through `t()`**: `src/renderer/src/simple/**` may hold no raw user-facing literal and only `common.*` / `simple.*` / `errors.*` keys (`simpleLint.test.ts`), and those values may not use the plan §1 banned words (`shared/simple/bannedWords.ts`: voucher, ledger, journal, contra, Dr/Cr, particulars, narration, sundry, group, ITC, set-off, ageing, BRS, godown, BOM, SOA — `i18n.test.ts`). Plain words for terms come from `shared/simple/glossary.ts` (`plain` / `explain`). Amounts are formatted by money.ts and passed in as variables; amount in words follows the print's language since WP 10.4. Accountant screens keep their literal English (not migrated).
- WP 8.0 correctness (both modes): registration rule (`shared/gst/registration.ts`, sources + UNVERIFIED list there): only a REGULAR registration charges GST, and the registration is effective-dated — `CompanyInfo.gstRegistrationSince` + `gstPreviousRegistrationType` (company meta JSON, no migration; set by `company:updateInfo` through `nextRegistrationFacts` when the type changes) and every rule tests the VOUCHER DATE (`registrationOn` / `chargesGstOn`). `InvoiceContext` carries the registration facts (spread `gstRegistrationOf(info)`); `computeInvoice` puts every line at 0% when the bill's date isn't GST-charging, and `saveVoucher` (`assertGstAllowed`) refuses a sales / purchase / note with CGST / SGST / IGST / cess lines then — except an alteration of a voucher that already carried tax (`legacyTax`: round-trips unchanged, editor warning) and a note set against a bill (bill ref or return line) of a GST-charging period or that carries tax (`taxedOriginal`, s.34). On such a purchase the supplier's GST is part of the cost: the editor's rates are GST-inclusive, capture folds each line's tax into its cost (`shared/capture/nonClaimable.ts`) — never an input-tax line. Counter billing, AI drafting and capture use the same path; Tally / books imports and import / bulk-edit undo restore history exactly (`historicImport` hook); payments / journals to GST ledgers stay allowed. GSTR-1 / 3B (`extractOutwardDocs`) and prints / e-docs (`extractEdocInvoices`) take a voucher's GST from the item master only when its date is GST-charging or it posts tax. Prints: composition → "BILL OF SUPPLY" with the r.5(1)(f) declaration, unregistered → "INVOICE", both without GST columns, tax table, CGST / SGST rows or place of supply. Registry `requiresGstRegistration` hides GST screens for unregistered companies. State pickers use `GST_STATE_LIST` (code order), never `Object.entries(GST_STATES)`. E2E scenarios that post tax lines create their company with `createCompanyUI(name, { gstin })`.
- Posted-tax rate for ledger-line documents (`shared/gst/postedRate.ts`, `postedLineRates` in services/gst.ts): an amount-only / accounting-mode sales invoice, credit note or outward debit note has no item master, and its sales ledger may carry no rate. When the voucher POSTS CGST / SGST / IGST (`tax_type` lines, net on the tax side) the rate-less sales lines (ledger `gst_rate` NULL — an explicit 0 is a declared nil / exempt line and never takes a rate) in `extractOutwardDocs` (GSTR-1, 3B, 9, HSN) and `extractEdocInvoices` (e-invoice / e-way, prints, receivables interest classes) take the rate the remainder of the posted tax (after the rated lines' own tax) implies — the nearest slab within the lines' rounding + ₹1 (rupee-rounded tax ledgers), the voucher date's slabs first, then any period's (a note at its 2025 bill's 12 %), sub-rupee round-off lines beside bigger ones left nil — else the implied rate (BigInt, 4 decimals) with `validation.offSlabRate` and the `off_slab_rate` warning in `gstValidate`; ledger rates stay for lines that have one and for vouchers that post no tax (ledger rate = fallback only); `gstPostedRateParity.dbtest.ts` pins every other document to a fixture generated from the pre-rule code (never regenerate it to pass); item-mode invoices, cess, SEZ/export WOP and the WP 8.0 `chargesGstOn` decision are untouched. Purchase-side readers (`extractPurchaseDocs`, `itcBreakdown`, `bookedItcByVoucher`, GSTR-2B matching) read the posted `tax_type` lines, never a ledger rate; only RCM self-assessment (`rcmInwardByVoucher`, `gstRcm.ts`) uses master rates, by design (an RCM purchase posts no input-tax lines).

Simple components live in `src/renderer/src/simple/` (the WP 8.2 lints apply; a registry key passed to `t()` sits on a line marked `i18n-technical`); simple Home is WP 8.6 (below).
- Field errors, save card, undo (WP 8.5, `src/shared/errors/`, migration 046 (undo_groups)): services throw `AppError(code, message, { field, params, issues })` with the message they always had (saveVoucher's posting-rule failures: code `validation` or the single rule's code, one issue per rule with its own message + line); `handle()` adds `code` / `field` / `params` / `issues` next to `error` (a ZodError → `invalid_input` + `zod.<code>` issues by path, a UNIQUE name clash → `duplicate_name`) and the renderer's `call` throws an `IpcError` carrying them. `codes.ts` `ERROR_MAP` maps every code to a field path (`date`, `number`, `party`, `account`, `items`, `lines.{line}.amount`, `billRefs`, `tds` …) and a plain `errors.*` key (+ `vars` / param-free `plainKey`); `errorMapping.test.ts` reads the codes from posting.ts / tcs.ts / withholding.ts / vouchers.ts / masters.ts / undo.ts / ipc.ts and fails on an unmapped one — a new code needs an entry and a message. `mapError` places issues on the fields a form shows (walking up the path) and returns the rest as `general`; **accountant screens keep the service's wording (fallback), simple screens only the `t()` text** (technical detail behind "Details"). Forms use `kit/useFormErrors(form, useErrorShell())` + `Field name/error` / `FieldError`: a message stays until its field's value changes; only what has no field becomes a toast. **Toast rule**: an error / warning raised while a dialog / drawer is open is scoped to that layer; when the layer closes it is RE-PARENTED to the layer below (or the screen), never dismissed, and it is dismissed when that screen goes (`kit/layers.ts` `onLayerClose`, nav subscription in stores.ts). Toasts raised with no layer open (a save warning right before `nav.replace` / `leave()`, background jobs) and success / info are never scoped — timer only. Save card (`simple/SaveCard.tsx`, sentences in `shared/simple/saveCard.ts`) shows after a NEW voucher is saved in InvoiceEntry / AccountingEntry only while the company is in simple mode (the toast otherwise); figures from `voucher:saveSummary` (saved vouchers + `partyAllocation` as on the latest saved voucher's date, never typed; EVERY debtor / creditor the vouchers touch is a party, cash / bank never); the editors save one voucher per save, so they pass `[id]` — Phase 9 intents pass all of theirs; Print = `invoice:pdf`, PDF / Share = `invoice:pdfBatch` (+ the sentences copied). **Undo** (`services/undo.ts`, `voucher:undoSave`, audited `voucher` delete per voucher + one `undo_group` row): bins the given vouchers through `deleteVoucher` (bin rules unchanged) as ONE group (`undo_groups` / `undo_group_vouchers`); offered only while every voucher's newest `voucher` audit row is still its `create` (edited / restored / matured since → "Edit instead"), for 24 hours after the save (`UNDO_WINDOW_MS`, then "Edit instead"), and while nothing outside the undo set rests on it (an `against` bill ref to its `new` ref, a `bank_statement_matches` row, a `line_links` row drawing on its lines → `undo_linked`, "Edit instead"); refused inside the lock, for a closing journal, and when a closing journal for its FY was created or restored AFTER the save by audit-row order (never re-opens a closed year); credit holds don't apply (binning creates no credit). `voucher:restore` goes through `restoreFromBin`: a voucher in an undo group restores the whole group in one transaction (all or nothing) and the group is dropped; any other voucher restores exactly as before. The bin lists `undoGroupId` / `undoGroupSize` (Settings → Bin shows an "Undone with N more" badge in the Account cell only for groups of 2+).

## Gotchas

- better-sqlite3 must match Electron's ABI. If the app throws `NODE_MODULE_VERSION` errors (e.g. after a plain `npm rebuild`), run `npx @electron/rebuild -f -w better-sqlite3`. `electron-builder install-app-deps` sometimes no-ops.
- npm blocks postinstall scripts (`allowScripts` allowlist in package.json covers electron, better-sqlite3, esbuild).
- `tally:import` and `bank:importCsv` IPC channels accept inline `xmlText`/`csvText` payloads so drivers can test them without native file dialogs.
- The e2e demo tour (`scripts/e2e/02-demo-tour.mjs`) seeds a `Demo Traders` company into the scratch data dir; reuse that seeding for manual checks instead of assuming one exists in `~/Documents/total` (it does not on every machine).
- The NIC live-filing client (`src/main/services/nic.ts`) is built to the published API spec (RSA + AES-ECB session crypto) but has **never run against the real portal** — no credentials. Treat as experimental; test on the NIC sandbox first.
- `TOTAL_DATA_DIR` (absolute path, read verbatim by `dataRoot()`) and `TOTAL_SUPPRESS_SYNC_WARNING=1` point driver/CI scripts at a scratch data dir and silence startup sync warnings — set both when scripting the app (see `scripts/smoke-ci.mjs`, `*.dbtest.ts`) so runs stay hermetic and don't touch `~/Documents/total/`. With `TOTAL_DATA_DIR` set the app also keeps Electron `userData` (localStorage etc.) inside the scratch dir. `TOTAL_INSECURE_TEST_SECRETS=1` (only honoured with `TOTAL_DATA_DIR` and an unpackaged build) swaps safeStorage for a test cipher so smoke/e2e never touch the keychain.
- Shells spawned by agent tooling may inherit `ELECTRON_RUN_AS_NODE=1`, which makes the app fail to launch under Playwright — run `env -u ELECTRON_RUN_AS_NODE npm run smoke` / `npm run e2e` in that case (`test:db` sets the flag itself on purpose). Since WP 7.3 the harness and smoke drop it themselves.
- `TOTAL_APP_EXECUTABLE` (absolute path to a packaged build's executable) makes `npm run smoke` / the e2e harness launch it instead of `out/`; `TOTAL_NO_UPDATE_CHECK=1` turns off the packaged app's startup update check (both set by the scripts, WP 7.3).
- `TOTAL_AI_MOCK=1` (only with `TOTAL_DATA_DIR`, unpackaged) swaps the OpenAI provider for the scripted demo `MockProvider` (`src/main/ai/mockProvider.ts`) — e2e 35 uses it. The default model ids `gpt-6.1-sol` / `gpt-6-luna` are unverified until Settings → AI → Test connection lists the key's models.
- After pulling Phase 5 changes run `npm ci` (then `npx @electron/rebuild -f -w better-sqlite3` if needed), or the app fails at launch with `Cannot find module 'openai'`.
- Recurring vouchers were removed in 0.5.0; migrations 008/009 and the `recurring_templates` table remain, untouched.

## Release steps (auto-update pipeline)

```bash
npm version patch|minor  # bumps version, commits, tags vX.Y.Z (minor for a phase release; latest tag: v0.11.0)
git push --follow-tags # → GitHub Actions: tests, DMG+ZIP build, publishes the release
```

- Before tagging, move `CHANGELOG.md`'s "Unreleased" section under the new version and date (every entry links its PR).
- `.github/workflows/release.yml` runs on `v*` tags (macOS runner, `GITHUB_TOKEN` automatic). `releaseType: "release"` in package.json `build.publish` — releases publish directly, **never leave them as drafts** (drafts are invisible to the `releases/latest` API that feeds updates and the site).
- Installed apps check for updates on launch (`src/main/updater.ts`): electron-updater first; because builds are unsigned, the working path on macOS is still the fallback — it asks the site's `/api/latest` and offers `/api/download`. Releases are public, so once an Apple Developer ID (`CSC_LINK`/`CSC_KEY_PASSWORD` secrets) exists and builds are signed, silent in-place updates take over.
- Updater consent (`src/main/updater.ts` wiring, `updaterCore.ts` pure flow, `services/appSettings.ts`, `shared/updates.ts`; renderer `simple/UpdateNotice.tsx` (mounted in `App.tsx` for every layout, both modes, strings `simple.updates.*` en/hi/hinglish) + `simple/UpdatesSetting.tsx` (How Total looks) + the accountant About checkbox): **nothing downloads or installs without a click** — `autoDownload` / `autoInstallOnAppQuit` are false (the latter flips only on "Install when I quit", which then re-runs the cached `downloadUpdate` — electron-updater arms install-on-quit only when a download completes); a failed download / install (unsigned macOS) turns into the release-page notice; electron-updater's per-install `x-user-staging-id` header is overridden with a constant (`NEUTRAL_REQUEST_HEADERS`); the notice's actions are hidden for non-owners and "Later" is session-wide (module-level, survives the layout swap); `update-available` / the site fallback become a notice (Download now / Later / Skip this version), `update-downloaded` another (Restart to update / Install when I quit / Later); "Later" is renderer-only. The app-level setting `updates` `{ autoCheck (default true), skippedVersion }` lives in `<dataRoot>/app-settings.json` (+ append-only `app-settings-audit.jsonl`; no company DB, no migration); with `autoCheck` off no request is made at launch ("Check now" still works). IPC `app:updates:get` (viewer) / `app:updates:set` / `app:updates:act` (owner where the company has users; Zod-strict; mapped as `read` in auditCoverage because they write no company audit row).
