# WP 2.5 — Sales and purchase cycles: written design

Date: 2026-10-07 · Status: **for review, no code yet** · Roadmap: WP 2.5 of
`2026-10-07-total-revamp-roadmap.md` · Code read against `origin/main` (`ef82a37`, migration 020)
plus `origin/p2/wp2.3-stock-visibility` (migration 021: serials). Migration numbers are assumed to be
**023 and 024**; the orchestrator assigns the final numbers.

The roadmap calls the line-linking and re-pricing rules "the riskiest design in this phase". This
document fixes those rules first (sections 2 and 3). Everything else follows from them.

---

## 1. Scope

**Sales cycle:** Quotation → Sales Order (SO) → Delivery Challan (DC) → Sales Invoice.
**Purchase cycle:** Purchase Order (PO) → Goods Receipt Note (GRN) → Purchase Bill.

Every step is optional and can be skipped: an invoice can be raised straight from an SO or with no
source at all (today's behaviour), and a bill can be raised from a PO with no GRN.

In scope:
- **Partial fulfilment.** Any source line can be drawn down in several pieces by several documents.
- **Many-to-many at document level.** One invoice can draw lines from several challans, and one
  challan can be invoiced by several invoices. At line level each target line has exactly **one**
  source line (§2.4), which is what keeps the rules simple.
- **Returns.** A credit note can be raised against sales-invoice lines and a debit note against
  purchase-bill lines. A rejection can also come in before invoicing: goods returned against a
  challan come back on a GRN whose line is a *return* of the challan line, and the mirror case
  applies to a GRN that has not been billed.
- **Closure.** A document can be short-closed (the rest of the quantity is abandoned) or
  cancelled (only allowed when nothing has been linked to it yet).
- **Reports:** pending sales and purchase orders, challans not yet invoiced, GRNs not yet billed,
  and three-way-match (PO ↔ GRN ↔ bill) exceptions.

Out of scope (later WPs or open questions): service-only order lines, landed cost (freight on the
bill loaded into stock), advance against order, proforma invoices, the job-work challans of WP 2.4
(they reuse the `delivery_note` kind and the `purpose` column defined here), blanket or scheduled
orders, and approval workflows.

## 2. Data model

### 2.1 Three classes of document

| Class | Documents | Where they live | Books effect |
|---|---|---|---|
| Non-posting | Quotation, SO, PO | new `trade_docs` + `trade_doc_lines` | none, ever |
| Stock-only voucher | DC (`delivery_note`), GRN (`receipt_note`) | `vouchers` + `inventory_lines`, **zero** `voucher_lines` | stock quantity and value only |
| Accounting voucher | Sales / purchase / credit note / debit note | unchanged | ledgers; stock only on lines with `moves_stock = 1` |

Orders go in their own tables, not in `vouchers`, because every one of roughly 100 `vt.kind`
readers, the trial-balance integrity check, Table 13, the day book and the voucher bin assume that
a voucher is a books document. Challans and GRNs *are* books documents, because they move stock,
so they are vouchers.

### 2.2 Voucher kinds: replace the CHECK list with a lookup table (migration 023)

Today the allowed kinds are a CHECK list inside `voucher_types` (migration 001). SQLite cannot
alter a CHECK constraint, so the table has to be rebuilt. WP 2.4 job work and future rejections
would each force another rebuild. The proposal is to **rebuild once** and replace the CHECK with a
foreign key to a `voucher_kinds` table, so that any later kind is a single `INSERT`.

**Runner change (required).** `migrate()` wraps each migration in `db.transaction`, and
`connection.ts` turns on `foreign_keys = ON`. `PRAGMA foreign_keys` is a silent no-op inside a
transaction. With foreign keys on, `DROP TABLE voucher_types` runs an implicit DELETE that
violates `vouchers.voucher_type_id` and `recurring_templates.voucher_type_id`. A deferred-FK
workaround does not help: the violation counter never drops after a RENAME. So the runner must
follow SQLite's documented 12-step table-rebuild procedure:

```ts
// migrate.ts — a migration whose SQL starts with this marker runs with FK enforcement off.
const FK_OFF = '-- @foreign-keys-off'
if (sql.startsWith(FK_OFF)) db.pragma('foreign_keys = OFF')      // outside the transaction
try {
  db.transaction(() => {
    db.exec(sql)
    const bad = db.pragma('foreign_key_check') as unknown[]
    if (bad.length) throw new Error(`migration ${i + 1}: foreign_key_check failed (${bad.length})`)
    db.prepare('INSERT INTO migrations …').run(i + 1, now)
  })()
} finally { if (sql.startsWith(FK_OFF)) db.pragma('foreign_keys = ON') }
```

`MIGRATIONS` stays a `string[]`. The marker is a comment, so `migrations.dbtest.ts` and the
`findIndex(sql.includes(…))` tests keep working. The runner also asserts
`PRAGMA legacy_alter_table` is 0 before it runs the migration.

**Migration 023:**


are unaffected. There are no triggers or views on the table (grep-verified).

**Risks of 023, and their mitigations:**
1. *The runner change touches every company open.* The marker path runs once per company. A
   dbtest covers both runner paths, plus a failure injected between DROP and RENAME, which must
   roll back to the old schema with foreign keys back on.
2. *Foreign keys are off during the migration.* `foreign_key_check` runs inside the transaction
   and aborts it if anything is orphaned.
3. *AUTOINCREMENT sequence.* The old `seq` is restored as above. A dbtest deletes a type before
   migrating and checks that its id is not reissued.
4. *Fresh companies.* `openCompany` runs `migrate()` **before** `seedCompany()`, so 023 inserts
   Delivery Note and Receipt Note with ids 1 and 2 ahead of the seeded ten. `DEFAULT_VOUCHER_TYPES`
   must **not** list them, or the seed would hit the UNIQUE name. This is cosmetic only, because
   pickers order by name.
5. *TypeScript drift.* `VOUCHER_KINDS` becomes a const array in `shared/domain.ts`, and
   `VoucherKind` is derived from it. A dbtest asserts that the `voucher_kinds` rows equal the array.
   Exhaustive `Record<VoucherKind, …>` maps then fail typecheck until they handle the new kinds,
   which is intended.
6. *Rejected alternative:* editing the CHECK text through `PRAGMA writable_schema`. It is
   undocumented-unsafe and corrupts the database if done wrong.

### 2.3 Lines get stable identities (migration 024, part 1)

`saveVoucher` **deletes and re-inserts** every `inventory_lines` row on edit, so line ids change on
every alteration. `serial_numbers` already copes with this by re-pointing its rows. A link keyed on
`inventory_lines.id` would be destroyed by any edit. The fix is a stable `line_uid`:

```sql
ALTER TABLE inventory_lines ADD COLUMN line_uid TEXT;
UPDATE inventory_lines SET line_uid = lower(hex(randomblob(16)));   -- backfill: legacy invoices can be returned against
CREATE UNIQUE INDEX idx_inv_line_uid ON inventory_lines(line_uid);
ALTER TABLE inventory_lines ADD COLUMN moves_stock INTEGER NOT NULL DEFAULT 1 CHECK (moves_stock IN (0, 1));
CREATE INDEX idx_inv_nonmoving ON inventory_lines(voucher_id) WHERE moves_stock = 0;
```

- `InventoryLineInput` gains `lineUid?: string`. On save, a uid is accepted **only** if it belonged
  to this voucher's previous lines (`before.inventory`). Otherwise the server generates a new one
  with `crypto.randomUUID()` and strips the hyphens. This stops a payload from stealing another
  voucher's uid.
- A uid is never NULL after 024. A dbtest asserts this, because the column is nullable only due to
  `ALTER TABLE` limits.
- `getVoucher` returns `lineUid`, `movesStock` and `source` (§2.4) on every `InventoryLine`. Every
  `voucherEdit` mode has to carry `lineUid` through its form state. If an editor drops it, the line
  looks new, its links fail validation, and the **save is refused**. That is the safe failure, and
  `voucherEdit.dbtest.ts` round-trips lines that carry links.

### 2.4 `line_links` (migration 024, part 2)

```sql
CREATE TABLE line_links (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  link_type TEXT NOT NULL CHECK (link_type IN ('fulfil', 'return')),
  from_trade_doc_id INTEGER REFERENCES trade_docs(id),           -- NO ACTION: a linked source can't be purged
  from_voucher_id   INTEGER REFERENCES vouchers(id),
  from_line_uid TEXT NOT NULL,
  to_trade_doc_id INTEGER REFERENCES trade_docs(id) ON DELETE CASCADE,
  to_voucher_id   INTEGER REFERENCES vouchers(id)   ON DELETE CASCADE,
  to_line_uid TEXT NOT NULL UNIQUE,                               -- one source per target line
  qty_milli INTEGER NOT NULL CHECK (qty_milli > 0),               -- = the target line's qty (entry fact)
  reprices INTEGER NOT NULL DEFAULT 0 CHECK (reprices IN (0, 1)), -- receipt_note → purchase only (§3)
  CHECK ((from_trade_doc_id IS NULL) <> (from_voucher_id IS NULL)),
  CHECK ((to_trade_doc_id IS NULL) <> (to_voucher_id IS NULL)),
  CHECK (from_line_uid <> to_line_uid)
);
CREATE INDEX idx_line_links_from_uid ON line_links(from_line_uid);
CREATE INDEX idx_line_links_from_voucher ON line_links(from_voucher_id) WHERE from_voucher_id IS NOT NULL;
CREATE INDEX idx_line_links_from_doc ON line_links(from_trade_doc_id) WHERE from_trade_doc_id IS NOT NULL;
CREATE INDEX idx_line_links_to_voucher ON line_links(to_voucher_id) WHERE to_voucher_id IS NOT NULL;
CREATE INDEX idx_line_links_to_doc ON line_links(to_trade_doc_id) WHERE to_trade_doc_id IS NOT NULL;
```

Each side of a link is "kind + line id", as the brief asked. It is spelt as two nullable foreign-key
columns plus a uid, so that each side gets real foreign-key behaviour: a purge of the target
cascades the link away, and a purge of the source is blocked.

**The target document owns its links.** Links are written by the target's save, inside its
transaction (`services/tradeLinks.ts → syncVoucherLinks(db, voucherId, input, before)`, called right
after `syncVoucherSerials`, and `syncTradeDocLinks` for trade docs). The links travel on the input
line:

```ts
// shared/posting.ts InventoryLineInput, and the trade-doc line input
source?: { lineUid: string; linkType: 'fulfil' | 'return' } | null
```

**Allowed pairs** (source kind → target kind). These live in `shared/tradeCycle/rules.ts` as data,
and anything not listed is rejected:

| link_type | source → target | target line `moves_stock` | `reprices` |
|---|---|---|---|
| fulfil | quotation → sales_order · quotation → sales | — / 1 | 0 |
| fulfil | sales_order → delivery_note · sales_order → sales | 1 · 1 | 0 |
| fulfil | **delivery_note → sales** | **0** | 0 |
| fulfil | purchase_order → receipt_note · purchase_order → purchase | 1 · 1 | 0 |
| fulfil | **receipt_note → purchase** | **0** | **1** (unless frozen, §3.4) |
| return | sales → credit_note · purchase → debit_note | 1 | 0 |
| return | delivery_note → receipt_note (rejection in) · receipt_note → delivery_note (rejection out) | 1 | 0 |

`moves_stock` is **derived by the server** and is not user input: it is 0 exactly when the line's
source is a stock-only voucher line and the link is `fulfil`. It is stored because about 12 SQL
readers need it (§2.6). It is written in the same transaction as the link, so it cannot drift. An
integrity dbtest checks `moves_stock = 0 ⇔ EXISTS fulfil link from a delivery_note/receipt_note line`.

**Invariants**, enforced in `tradeLinks.ts`. Each one throws, which rolls the save back:

- I1 **Capacity.** For each source line,
  `Σ live fulfil qty + Σ live return qty ≤ source qty`. For orders and invoices,
  `Σ live fulfil ≤ qty` and `Σ live return ≤ qty` are checked separately. *Live* means the target
  is a voucher with `deleted_at IS NULL AND is_optional = 0`, or a trade doc with
  `deleted_at IS NULL AND status <> 'cancelled'`. Post-dated targets count, because they reserve
  quantity the same way they reserve serials.
- I2 **Same party, same item.** Source and target share `party_ledger_id` and `stock_item_id`.
- I3 **Same physical goods** when `moves_stock = 0`. The target line's godown and batch equal the
  source's, and its serials are a subset of the source line's serials, sized to the quantity. Serial
  lines with `moves_stock = 0` are stored so they print, but `rebuildItemSerials` **skips** them.
- I4 **Link qty = target line qty.** Over-delivery is a separate, unlinked line.
- I5 **Source open.** No new link may be made to a source that is binned, cancelled, or short-closed
  (§2.7). Links that already exist survive a later close.
- I6 **No links on optional (memorandum) vouchers** and no links on `physical_stock` or
  `stock_journal`.
- I7 **Dates.** If the target is dated before the source, the save goes through with a warning
  (`warnings.linkDates`). The only hard effect is on return costing, §3.3.

**Lifecycle:**

| Event | Rule |
|---|---|
| Edit target | Delete the voucher's own links (`to_voucher_id = ?`) and rebuild them from input, then re-check I1–I7. |
| Edit source | Every uid still linked from live or binned targets must remain, with the same item (and the same godown, batch and serials when a non-moving target uses it), and qty ≥ Σ linked. Otherwise refuse: "DC-12 line 2 is invoiced by INV-40; bin that first". |
| Bin target | Allowed. Its links go dormant (not live), so the source's pending quantity reappears. |
| Bin source | **Refused** while any live target links to it. |
| Restore target | Re-validate its links. Refuse if a source is binned or purged, or if capacity has since been taken by another document. This mirrors the serials-restore refusal. |
| Restore source | Always allowed. |
| Purge target | `ON DELETE CASCADE` removes its links. |
| Purge source | Blocked by the foreign key while any link, even from a binned target, references it. `purgeOldDeleted` already continues past FK failures, and manual purge shows the reason. Without this, restoring the binned target would leave a `moves_stock = 0` line with no source, and its stock would vanish. |
| Lock date | See §3.4 for repricing links. Ordinary links follow the target's own date. |

### 2.5 Choice: `moves_stock` flag (chosen) vs. invoice without inventory lines

**Option B**, where the invoice has no `inventory_lines` and only a link, leaves the stock readers
alone. It breaks everything that reads the invoice's items:
- the GSTR-1 HSN summary and B2B items (`gst.ts:102`, `:251`)
- e-invoice and e-way item lists (`edocs.ts:197`)
- print and discounts (`printTemplates.ts:252`)
- item profitability and the suggested sale rate (`reports.ts:205`, `manufacture.ts:86`)
- search by item
- `invoiceStateFromVoucher`, which refuses "it has no item lines"

The invoice's own rate and discount also differ from the challan's, so they would need a new
invoice-item table, which is Option A under another name.

**Option A** (chosen) keeps the invoice a complete invoice. The cost is a filter in every reader
that means *stock movement*. That risk is real: a missed filter double-counts stock. It is managed
with:
- `export const MOVES_STOCK = 'il.moves_stock = 1'` in `vouchers.ts`, next to `IN_BOOKS`.
- **A lint test**, `src/main/services/movesStockLint.test.ts` (pure, reads source text). Every SQL
  template in `src/main/services/*.ts` that mentions `inventory_lines` must contain `MOVES_STOCK` or
  `moves_stock`, or sit on an allowlist in the test with a one-line reason. Initial allowlist: gst,
  edocs, printTemplates, search, masters (usage counts), `manufacture.suggestedSaleRate`,
  `reports.itemProfitability` sales leg, and serials' lookup queries.
- A dbtest that saves challan + invoice and asserts the stock summary, batch stock, godown stock,
  movement register, ageing, reorder and negative-stock figures all equal the challan-only figures.

## 3. Valuation: GRN repricing and return costing

### 3.1 The rule

A GRN line `G` (qty `Gq`, stored amount `Ga` = PO or GRN rate × qty − discount) enters stock at
`Ga` until it is billed. Bill lines `B₁…Bₖ` linked to it with `fulfil, reprices = 1`, and live,
**reprice** it:

```
billedQ = Σ Bᵢ.qty        (≤ Gq by I1)
billedA = Σ Bᵢ.amount     (taxable ₹, net of discount, excluding GST)
value(G) = billedA + (Ga − round(Ga × billedQ / Gq))         -- proportional; exact integer paise
```

Example: GRN 10 units @ ₹100 = ₹1,000, bill 6 @ ₹110 = ₹660. Then
`value = 660 + (1000 − 600) = 1,060`. Once fully billed, `value = billedA` exactly.

**GST excluded, always, in v1.** A direct purchase invoice stores `inventory_lines.amount` =
taxable value and never capitalises GST, even when the party's `itc_eligibility = 'blocked'`. If
the GRN path capitalised blocked GST, the same goods would value differently by route. Consistency
with the direct path, and the legacy-unchanged guarantee, come first. Capitalising blocked ITC on
both paths is open question Q3.

### 3.2 Engine change (`src/shared/valuation.ts`)

```ts
  /** Outward lineIds whose engine-charged cost the pass must remember (sources of returnOf). */
```

- In `InventoryPass.run`, rule `'linked'` processes lines in their stored order, like `'stored'`.
  Each plain inward line with a `LinkedLineCosting` enters at `linkedInwardValue(…)`, or at
  `round(cost(sourceLineId) × q / sourceQtyMilli)` for a return. Lines without one enter at their
  stored amount. Booked values go to `inwardValueByLine`, so the godown view and the movement
  register agree.
- `outward()` already returns the charged cost. When `m.lineId ∈ costSources`, the pass records it
  in `outwardCostByLine`. If a return is processed before its source, which can only happen when
  the return is dated earlier (I7), it falls back to the stored amount and is reported in a new
  `InventoryPassResult.linkedFallbacks: number[]`. The register shows a warning chip for these.
- `bookedInwardValues` stays pass-free for `billed`-only costing, because the value depends only on
  the link facts. Any `returnOf` forces the full pass, the same as `'derived'`.
- **Value conservation:** `'linked'` only chooses inward amounts. `ItemCostState` stays the single
  place value moves, so `opening + Σinward = consumed + closing` still holds. The property test
  extends `valuationPass.test.ts` with random linked vouchers.

### 3.3 Loader (`stockAnalysis.ts`)

`voucherCosting(db, asOn)` gains a third source, `linkedCostingSource(db)`:
- **GRN repricing:** for every live (`NOT_DELETED`) `receipt_note` line that has live
  `reprices = 1` links, read the live bill lines' `qty_milli` and `amount`.
- **Return costing:** for every live inward line with a `return` link (rejection-in GRN, credit
  note), resolve the cost source by walking `fulfil` links upward from its source line to the first
  `moves_stock = 1` line. Example: credit note → invoice line (non-moving) → challan line. Add that
  line to `costSources`.

**Independent of `asOn`.** The bill's date does not gate the repricing. Gating on it would break
the invariant `runInventoryPass` relies on, that a checkpoint snapshot equals a pass over the
movements up to it (`stockValuesAt`, `periodConsumption`). The repricing is retroactive to the GRN's
position. Consumption between GRN and bill is re-costed at the billed price. This is what the
roadmap asks for ("handles reprice-at-valuation-time").

### 3.4 Order-of-events and edge cases

| Case | Behaviour |
|---|---|
| Bill dated before GRN | Allowed, with a warning (ITC needs receipt of goods, s.16(2)(b) CGST Act, *cited from memory, unverified*). The repricing is unaffected because it is positional at the GRN. |
| Partially billed | Proportional formula. The unbilled share stays at the GRN rate. |
| Bill binned or made optional | The link is not live. The GRN reverts to stored value for that share, and the GRN shows as unbilled again. |
| Bill restored | Re-check I1. Repricing returns. |
| GRN edited after billing | Allowed for rate or amount (only the unbilled share moves) and narration. Qty below billed qty, or a change of item, godown or batch on a billed line, is refused. |
| GRN binned | Refused while live bills link to it. |
| **Locked periods** | Repricing changes stock value at the GRN's date. (1) When a bill links to a GRN dated on or before the lock date, or in an FY with a live year-end closing journal, the link is saved with `reprices = 0` (frozen). The difference then flows through COGS of the bill's period, which is ordinary periodic-stock behaviour, and the bill shows a "price difference not loaded into stock (period locked)" note. (2) Saving, binning or restoring a bill whose `reprices = 1` links point at a GRN that is **now** inside the lock is refused unless every such link's (qty, amount) is unchanged. Rationale: a later edit must not move locked figures. `reprices` is an entry fact fixed at link time, so values never depend on where the lock currently sits. |
| Foreign-currency bill | `inventory_lines.amount` is already base ₹ (`computeInvoice`). |
| Debit note against bill | Goods out, costed by the engine at the current average or FIFO layer. Unchanged. The GRN is not re-priced. |
| Freight or other charges on the bill | Not loaded (Q4). |

**Legacy proof.** Before 023 no `receipt_note` voucher and no `line_links` row can exist, and every
existing line gets `moves_stock = 1`. So `linkedCostingSource` returns nothing, the loaders read the
same rows, and the pass is byte-identical. This is asserted by the legacy oracle
(`valuationLegacyOracle.testutil.ts`) and by a migration dbtest that snapshots `stockSummary`,
trial balance, P&L and GSTR-1 JSON for a Demo Traders copy before and after 023–024.

## 4. GST and documents

### 4.1 Legal basis

Sources are secondary reproductions of the CGST Rules text: [gstzen R55](https://gstzen.in/a/transportation-of-goods-without-issue-of-invoice-cgst-rule-55.html),
[caclub R55](https://caclub.in/cgstrules/42262/rule-55-of-cgst-rules-2017-transportation-of-goods-without-issue-of-invoice/),
[gstzen R138](https://gstzen.in/a/information-to-be-furnished-prior-to-commencement-of-movement-of-goods-and-generation-of-e-way-bill-cgst-rule-138.html).
**I did not retrieve the official CBIC text.** The implementer must check these against
cbic-gst.gov.in before shipping.

- **Rule 55(1).** A delivery challan may be issued *in lieu of invoice* for liquid gas of unknown
  quantity, job work, transport "for reasons other than by way of supply", and notified cases. It
  is "serially numbered not exceeding sixteen characters, in one or multiple series". It carries
  date and number, consigner and consignee name, address and GSTIN, HSN and description, quantity
  (provisional if unknown), taxable value, tax rate and amount "where the transportation is for
  supply to the consignee", place of supply for inter-State movement, and signature.
- **Rule 55(2).** Triplicate copies: ORIGINAL FOR CONSIGNEE / DUPLICATE FOR TRANSPORTER /
  TRIPLICATE FOR CONSIGNER. **55(3):** declared for the e-way bill per rule 138. **55(4):** where
  goods move for supply but the invoice could not be issued at removal, the supplier issues the tax
  invoice after delivery.
- **Rule 138(1).** An e-way bill is needed for movement of goods of consignment value **exceeding
  ₹50,000**, "in relation to a supply, for reasons other than supply, or due to inward supply from
  an unregistered person". Consignment value is the value "declared in an invoice, a bill of supply
  or a delivery challan", including tax. This matches the existing `EWB_THRESHOLD_PAISE`.
  *Unverified:* the proviso requiring an e-way bill for inter-State job-work movement regardless of
  value, and the state-specific intra-State thresholds.
- **Design consequence (honest risk).** For an ordinary sale, s.31(1)(a) CGST Act requires the
  invoice at or before removal (*from memory, unverified*). A "challan now, invoice later" flow for
  a plain supply is therefore only partly supported by 55(4). The app allows it, warns when the
  invoice is dated after a `purpose = 'supply'` challan, and never treats the challan as a tax
  invoice. Supply on approval (s.31(7): invoice within 6 months of removal, *unverified*) gets a
  pending-report column for days since removal.

### 4.2 Effects on returns and e-documents

- **GSTR-1 and 3B** read kinds `sales`, `credit_note` and `debit_note` (and purchase kinds for
  ITC), so delivery and receipt notes are excluded by construction. Invoice lines with
  `moves_stock = 0` still feed the HSN summary, which is correct. A dbtest covers both.
- **Table 13** (`extractDocSeries`): `GstDocSeries.category` widens to `1|4|5|9|10|11|12`. Challans
  are reported by purpose: `job_work` → 9, `approval` → 10, `liquid_gas` → 11, `non_supply` and
  `supply` → 12. The nature-of-document codes come from the portal's Table 13 list and are
  **unverified**. Mapping `supply` to 12 is questionable (Q6). GRNs are not outward documents and
  are not reported.
- **E-way bill from a challan.** `listSalesInvoices` and `buildEwbJson` accept `delivery_note`:
  `docType: 'CHL'`, `supplyType: 'O'`, and `subSupplyType` from purpose (supply 1, job work 4,
  others 8 with `subSupplyDesc`). These are NIC EWB master codes, **unverified**, to be checked
  against the NIC sandbox master. Value and tax are computed from the challan lines and item rates
  (rule 55(1)(vi)–(vii)) and not posted. E-invoice (IRN) never applies to a challan.
- **E-way bill on the later invoice.** When every goods line of an invoice has `moves_stock = 0`,
  `ewbReason = 'Goods moved on challan DC-x'` (with the challan's EWB number if it has one), so no
  second e-way bill is generated.
- **Number length.** For `delivery_note` and `sales` series, warn when a generated or typed number
  exceeds 16 characters (rule 55(1), and the same limit for invoices under rule 46(b), *unverified*).

### 4.3 Numbering, printing, import

- **Numbering per kind.** Each kind has its own series: Delivery Note and Receipt Note voucher
  types, plus the three `trade_doc_types`. All use the F11 prefix, suffix, pad and restart knobs.
  The Masters "Voucher types" tab lists trade-doc types in a second section.
- **Print.** `PRINT_DOC_KINDS` appends `'sales_order', 'purchase_order', 'goods_receipt'`. The
  existing `'delivery_challan'` and `'quotation'` placeholders become live.
  `printKindForVoucherKind` gains an explicit map: `delivery_note → delivery_challan`,
  `receipt_note → goods_receipt`. A new `loadTradeDocPrint(db, company, docId)` builds the same
  invoice-shaped `PrintDocument`, without outstanding, IRN or bank QR. Templates gain an optional
  `copyLabels: string[]`, defaulting to the rule 55(2) triplicate for `delivery_challan`, which
  prints one page set per label. Terms and validity print on quotations and orders.
- **Tally import.** `kindForName` currently maps "Receipt Note" → `receipt` and "Delivery Note" →
  `journal`, and maps "Sales Order" and "Purchase Order" → `sales` and `purchase`, which is wrong
  today. Match `delivery note`, `receipt note` and `rejection` first. Orders are skipped with a
  warning in v1 (Q8).

   Tally-style periodic stock, an unbilled GRN raises closing stock with no purchase booked; the
   accountant posts a provision. *(I could not verify how Tally itself treats this.)*
6. **Q6. Table 13 category for `purpose = 'supply'` challans?** **12, with a "confirm with your
   CA" note.** Verify the nature codes on the portal before release.
7. **Q7. Serial status after a challan?** **`'sold'`** (the CHECK has no `'delivered'`, and adding

   column.

   Outstandings stay invoice-based.

    Tally (*unverified*). Mention it in the changelog. 11-keyboard is updated.
11. **Q11. Do returns re-open SO or PO pending quantity?** **No.** A replacement needs a new order
    or an unlinked line.
12. **Q12. Service (non-stock) lines on quotations and orders?** **Not in 2.5.** `stock_item_id`

13. **Q13. Should a challan's stored rate be the SO rate or the item's cost?** **SO rate, or the

14. **Q14. Feature flag default for new companies?** **Off.** Turning on `inventory` suggests it
